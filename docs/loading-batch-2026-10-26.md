# 加载与批量并发改进

本轮从 `b687d4c` 测量并改进本机加载和独立多文档转换。文档不上传，未添加运行服务；新增精确固定的构建期开发依赖 esbuild，用于将应用模块打成一个本地 ESM 文件。用户运行 Windows 或 Android 包不需要它。

## 批量使用

在设置侧栏选择“批量转换 · 多文档并行”，添加 Markdown、PDF 及相关图片后开始处理。原工作台文档不被替换；每份任务独立显示进度、问题、预览和下载入口。关闭面板后任务继续；刷新或关闭页面前应下载结果。

- 最多保留 20 份文档。桌面默认并发 2 个任务，Android 默认 1 个，均可选择 1 或 2。
- 桌面输入总量 120 MiB，Android 60 MiB；图片仍最多 256 张、80 MiB。结果与 HTML 预览合计保留上限为桌面 120 MiB、Android 80 MiB，达到限制的任务明确失败，已有结果保留。
- 同名输出自动增加序号。图片按完整相对路径匹配；重复图片路径会在修改队列前拒绝，不能用最后选中的图片静默覆盖先前文档。不同文档使用同名图片时应保留目录结构选择。
- 可取消单项或全部；取消中的任务等待后台清理，之后才能重用名额。失败或已取消任务可重试，不影响其他结果。
- 缺图、公式错误或引用的无效图片进入“需核对”。逐项确认后可带问题下载；一键 ZIP 只包括可直接导出的结果，明确说明排除数量。无关损坏图片不会阻止另一份正常文档。
- 参数在开始时捕获，批量 PDF 不沿用工作台旧页码范围。需要选页时仍使用单篇工作台，或先拆分文件。
- 清空结果需确认，并释放任务、资源索引与预览的引用。结果不写入本机草稿；本机草稿仍只保护原工作台。

## 加载机制与实测

公开静态资源使用内容 SHA-256 ETag 与 `private, no-cache` 条件缓存。文件即使大小和时间戳相同，只要字节改变，也会返回新资源。API、PDF 结果、示例和错误仍禁止缓存。应用模块由构建期打包为一个文件，功能按需初始化，Android PDF.js 引擎仅在真正转换时加载。独立启动边界显示加载失败和重新加载入口，不自动重试或清除草稿。

同一主机、Edge、示例文档，优化前后各 3 个新浏览器上下文，分别首次打开和刷新：

| 测量 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 刷新资源传输量 | 2,269,471 字节 | 12,590 字节 |
| 刷新就绪时间中位数 | 504 ms | 408 ms |
| 首次就绪时间中位数 | 739 ms | 602 ms |
| 页面资源请求数 | 29 | 13 |

刷新传输量降低约 99%；应用自身不再请求分散的 `/modules/*`。仍有条件请求，不能把 304 当作零请求。时间仅为三个本机样本，不是所有文档、设备的加速承诺。

另外对 9 个固定延迟 SVG 做受控测试：首次索引 481.2→187.9 ms，最大重叠读取 1→3；相同 File 再次索引 484.1→低于 1 ms，两次读取次数 18→9。整个页面共享三个读取/解码名额，两个独立索引同时构建时峰值也不超过三个。该延迟用于隔离并发机制，不等同于真实磁盘速度。缓存以不可变 File 身份为键；失败不缓存，不按同名文件猜测复用。无公式文档不再等待另一份文档的 MathJax 队列；包含公式的文档仍按顺序排版，保留编号隔离。

## 并发边界

桌面两个 PDF 使用独立子进程，继续保留原有上传、页数、超时、结果与临时文件限制；第三个请求返回具名容量状态，批量队列仅对这种容量响应进行有界等待，期间查询轻量 `/api/pdf/capacity`，不反复重传大文件。取消一个任务不会错误释放另一个任务的名额，关闭服务须排空任务。

每个子进程原有内存上限为 1.5 GiB，两个子进程合计最高 3 GiB，另有浏览器和父进程内存。内存紧张时选择单任务；源码 `create_server(..., pdf_workers=1)` 也支持单名额。并发会竞争 CPU 和磁盘，不能保证吞吐等比例增长。浏览器主线程 Markdown 解析、共享 MathJax 公式排版并未变成任意多核执行。

## 验证

- Python 全套 57 项，含两个真实同时转换的 PDF、第三项容量拒绝、轻量状态、取消隔离、上传/关闭保护、强制关闭子进程、ETag 变化与隐私缓存边界。
- 浏览器测试最终集合共 114 项。涵盖队列重叠、同名结果、实际下载 ZIP、真实双 PDF、单项取消、目录图片、错误隔离、清空/重试、容量等待不重传大文件、键盘焦点、安卓预览返回、单应用 bundle、加载错误恢复、模块副本共享 MathJax，以及既有离线与安全回归。
- 独立审查发现的重复图片覆盖、无关资源诊断污染和清空资源引用均已修正；对应可观察行为补回归，资源引用释放经代码审查核实，未声称测得垃圾回收后的 RSS。
- Windows CI 将同一完整浏览器集合分为三个独立作业并行执行，自动重试保持关闭；Windows Python/打包、Android 和依赖审计各自保留检查。合并前及合并后主分支均须核对结果。
- 初次 PR 的一个分组在首页加载 `zip.js` 时再次报告客户端 `ERR_NO_BUFFER_SPACE`，没有进入 PDF 转换。仅缓存和分组不能据此视为已修复；随后合并应用模块请求，并增加显式启动失败入口。未从操作系统层证明缓冲区错误来源，不宣称任何网络故障都已消除。
- 本机 Windows/Android 验证产物单独存放，不覆盖历史 Release 附件；Android 原生 PDF 系统选择器返回阶段仍不在本轮验收结论中。

开发者修改 `web` 源码后运行 `npm run build:web`；初次准备使用 `npm run prepare:vendor`，它也会构建应用 bundle。Windows 构建脚本在打包前重新生成 bundle，避免把旧生成文件随新源码发布。
